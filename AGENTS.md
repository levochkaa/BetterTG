# BetterTG Agent Instructions

> `CLAUDE.md` is a symlink to this file, so Codex and Claude Code read the same rules.

## Build And Test

- Build and run through ./build.sh as described below. T3 Code's Device panel (DeviceHub), idb, XcodeBuildMCP and Xcode MCP tools, including device interaction, may be used for Simulator validation such as UI inspection, taps, gestures and screenshots.
- Read Simulator and device screenshots as reduced copies: downscale before viewing (for example `sips -Z 1000 -s format jpeg shot.png --out shot.jpg`) and crop to the region of interest when only part of the screen matters. Full-size screenshots hit the image limit and cost more tokens.
- Build through the root multiplexer: `./build.sh build` (or `./build.sh`, which defaults to build).
- Run through the root multiplexer: `./build.sh run`. BetterTG currently has no dedicated test target, so build is the repository-level validation.
- Always run SwiftFormat after modifying Swift files. Pass every existing `.swift` file modified in the current task to a single invocation, and do not format the entire repository unless the user explicitly asks for it:

  ```sh
  swiftformat --config .swiftformat --cache ignore "path/to/File.swift" "path/to/File2.swift" "path/to/File3.swift"
  ```

- Before finishing any task, run `./build.sh build` after formatting to verify that the project compiles successfully. If the user explicitly asks not to build, follow that narrower scope and report that build verification was skipped.
- Treat every warning emitted by `./build.sh build` as a handoff blocker. Fix the warning and rerun the build before treating the task as complete; a successful build that still contains warnings is not a clean build. Do not silence or suppress warnings merely to make the output quiet. If a warning comes from external code and cannot be fixed safely within the task scope, report it as a blocker and ask the user how to proceed instead of claiming completion.
- The build script owns Xcode environment setup, project generation, TDLib model generation, package resolution, derived data location, and simulator selection.
- TDLib update notification bindings are generated by `script/td.py`; the build wrapper runs it against the resolved TDLibKit schema.
- Pass all build and run overrides as wrapper options; never prefix `build.sh` with configuration environment assignments. Available overrides include `--xcode`, `--configuration`, `--simulator`, `--simulator-id`, `--ios`, `--device-id`, `--derived-data`, `--cloned-source-packages-dir-path`, `--xcodebuild-log-dir`, `--launch-argument`, `--console`, `--no-code-signing`, `--skip-build`, `--simulator-boot-timeout-seconds`, and archive's `--archive-path`, `--build-number` and `--authentication-key-*`.
- Use `./build.sh build --device` to build for the available paired physical iPhone and `./build.sh run --device` to build, install, and launch on it. Device builds use Xcode automatic provisioning. Pass `--device-id ID` only when a specific physical iPhone must be selected.
- `./build.sh archive --archive-path PATH` archives a Release build for distribution. The fastlane lanes call it to ship TestFlight and App Store builds; `docs/releasing.md` describes them.
- Put app arguments after the `--` delimiter when an automated launch smoke needs them; repeated `--launch-argument VALUE` options remain available for compatibility. Do not bypass `build.sh` with a direct simulator launch.
- Use `./build.sh run --device --console -- ARGUMENT...` when physical-device stdout/stderr must remain attached for live diagnostics. The command intentionally waits until the app exits.
- Swift packages are cached separately from DerivedData by a graph hash containing the `project.yml` package declarations, including the exact TDLibKit 2 version, and exact Xcode version. Reuse the graph cache and restored `Package.resolved`; do not delete or redownload it when clearing DerivedData.
- Default DerivedData and module caches are isolated by Xcode version. Build and run actions serialize the generate/package/codegen/xcodebuild portion through `/tmp/bettertg-build.lock`; install, launch, and attached console run after the lock is released.
- Builds from every worktree share one C/C++/Objective-C compilation cache per Xcode build in `~/Library/Caches/BetterTG/CompilationCache` (20 GB cap, pruned by Xcode), so a new worktree reuses libwebp and the bridges compiled elsewhere. Swift caching stays off in `project.yml`: with C++ interop Xcode 27.1 warns on every cached Swift job. The worktree path is recorded as `/^root`; in LLDB run `settings set target.source-map /^root <worktree>` before a full-path breakpoint or source listing in C-family code.
- `docs/screenshots` holds the README's screenshots, all made-up data from `BetterTG/Services/ReadmeDemo.swift`. To retake them, launch a Debug build with `-readme-demo` on a simulator with no account: the client stays signed out and never reaches the push relay. Never launch it on a simulator or device with a session. A screen that needs more data adds its request to `DEMO_REQUESTS` in `script/generate_tdlib_client_compat.py` and answers it in the demo.
- Compiling builds fail below 5 GiB of free disk without deleting anything; pass `--minimum-free-disk-gb 0` only when the space is known to be enough. `./build.sh clean-cache` removes caches no worktree uses: DerivedData, module and compilation caches of other Xcode versions, other worktrees' DerivedData unused for 15 minutes (`--cache-recent-grace-minutes`), and BetterTG package graph caches other than the current one; other projects' package caches in the shared root stay. Preview it and `clean-intermediates` with `--dry-run`.
- Xcode builds print compact progress and save complete command output under `.build/logs/xcodebuild`; use `--full-output` only when the complete stream is needed in the terminal.
- Debug builds use `-O1` for C/C++, including Swift-package targets, to bound stack usage in TDLibKit's generated recursive schema cloning. Swift retains Debug's `-Onone` settings.
- Compact output must retain every build warning. Check the complete log before claiming a warning-free build. The notification extension declares no AppIntents and skips that inapplicable metadata stage; restore extraction if AppIntent declarations are added.
- `./setup.sh` configures a checkout: it writes the Telegram `api_id` and `api_hash` to the ignored `BetterTG/Secret/Secret.swift`, and a fork's Team ID, bundle ID and push relay to the ignored `Configuration/Local.xcconfig`, which overrides `Configuration/BetterTG.xcconfig`. `./setup.sh --help` lists its options.
- Codex worktree setup and T3 Code's Setup worktree script (`t3.json`, run on worktree creation) run `./script/prepare_worktree.sh`. Project generation also runs it so existing worktrees self-heal. The script copies a missing `Secret.swift` and `Local.xcconfig` from the primary checkout and never overwrites an existing file.
- Use `./build.sh clean-intermediates` to remove compilation/index/module/SDK-stat intermediates while preserving app products, complete logs, and the separate Swift package cache. `./build.sh run --skip-build` reuses the compatible product for the selected Xcode, configuration, and platform without running XcodeGen, package preparation, TD generation, or xcodebuild.
- Simulator runs wait for bounded `simctl bootstatus` readiness before install. Do not close or shut down the booted Simulator when finishing a task unless the user explicitly asks.
- Simulators run headless: `build.sh` never opens Simulator.app, and agents must not launch it. Watch a Simulator in T3 Code's Device panel (DeviceHub) and drive it with idb or XcodeBuildMCP.

## iPhone Duo

- `IPhoneDuoLayout` (`BetterTG/Views/Common/IPhoneDuoLayout.swift`) holds the posture table and the system's vertical bar metrics. Every other device gets nil, so a Duo fix must reduce to the old expression with no side insets.
- A portrait-only app still gets landscape on the unfolded screen: a plain unfold lands in 951x669, which is regular width, and `requestGeometryUpdate` is refused there. Folded portrait has an 84 pt right inset. Nothing may assume "portrait has no side insets" or read a size once.
- Bars' rows start 24 pt from the top in every posture. Only unfolded landscape has the side column: back and icon buttons go into it there and text buttons stay in the row. Folded, every button stays in the row. A chat keeps its bar in the row in every posture, as it would otherwise jump with the keyboard. A menu from a column button opens in the button's place, over the strip, and one from a bar button beside the island stands on the button above the safe area: a menu's stack must not inset its margins from the safe area.
- Content keeps to the band between the side insets. The chat list's folder tabs at the bottom edge span the strip unless a corner block reaches their row (`bottomEdgeRightInset`). The attachment sheet's tabs and a floating composer stay in the band.
- Beside the unfolded portrait island, trailing buttons stop right at it, the title centres between the buttons, and the root's top safe area puts the search field under the row below the island at full width (`islandSafeTop`, `rowTopOffset`); an open search takes the row and keeps clear of the island. The status corner changes with what it shows, so `IPhoneDuoLayout` grows its table values from the live `reservedRegions(kind: .occlusion)` and the root relayouts the bars when they change.
- The side column and the row live apart: a push or pop never morphs a button from one to the other. Column shapes pair only with column shapes, by position. Elsewhere a title centers on the band, over the list, not on the screen.
- A self-sizing input view keeps its frame's width: resize it on a size transition. A full-screen modal calls `applyIPhoneDuoTopSafeArea()`, since only the root and its children inherit it.
- `TelegramSplitViewController` shows two columns on a window wider than 690 pt and taller than 650 pt (Telegram's `layoutMetricsForWindowSize`), which on the Duo is unfolded landscape, with the column boundary on an active vertical fold. `NavigationStorage.navigationController` is the list pane's stack; `activeNavigationController` is where new screens go, and `NavigationStorage.shared.viewControllers` lists both panes. A list row opens with `push(_:fromList: true)`, and `TelegramMasterPaneScreen` keeps a list in the list pane.
- Screens move between the panes as the window folds or rotates. Teardown tied to leaving navigation checks `isLeavingNavigation` or `TelegramNavigationController.isRelocatingScreens`, not `isMovingFromParent` or `parent == nil` alone. A screen must be off its old stack before the new one adopts it, or UIKit leaves it marked disappeared on screen, where it stops following the safe area.
- `docs/iphone-duo-layout.md` in Telegram-iOS is the reference for the rules and postures.

## Git Workflow

- Commit all agent-authored changes before handing the task back to the user, unless the user explicitly asks to leave changes uncommitted.
- For a large task, commit after every coherent, verified implementation stage. Do not wait until the end and put the entire large task into one oversized commit.
- Keep every commit focused and stage only the files or hunks that belong to that stage; never include unrelated user changes.
- Name commits as `<type>(<scope>): <imperative summary>`, with `feature`, `fix`, or `tech` as the type and a concise lowercase scope.
- Keep the summary lowercase, imperative, and specific to the delivered behavior or technical change.
- End every agent-authored commit with a `Co-authored-by:` trailer naming the model that wrote it, such as `Co-authored-by: Codex <noreply@openai.com>`.

## UI Implementation

- Implement all application UI in UIKit. Do not introduce SwiftUI, `UIHostingController`, `UIViewRepresentable`, `UIViewControllerRepresentable`, or other SwiftUI-only UI and layout code.
- Keep UI implementations UIKit-native, using `UIViewController`, `UIView`, `UITableView` or `UICollectionView`, Auto Layout, and Combine-based observation where appropriate.
- Use the official Telegram iOS source code as the primary behavioral and layout reference. Inspect a sibling `../Telegram-iOS` checkout when available, and port the relevant logic instead of replacing it with a simplified approximation.
- Adapt referenced Telegram behavior to BetterTG's UIKit and TDLibKit architecture; do not copy unrelated Telegram infrastructure into the project.
- "Interactive glass" means Liquid Glass's press response, `UIGlassEffect.isInteractive`: the glass swells and brightens under the finger. It is not `isUserInteractionEnabled` or a control's touch handling. Telegram makes its glass interactive (`isInteractive: true`) on the bar buttons, the chat's history buttons and the composer's capsules and buttons.
- `isInteractive = true` alone is not enough. UIKit drives the response from a pan recognizer it adds to the window (`_UIFlexInteraction`), and that recognizer reacts only to a touch whose hit-test view lies inside the glass view. Put the content in the glass's `contentView` and keep the glass's user interaction enabled. Glass that sits under a button, or has `isUserInteractionEnabled = false`, never responds. A menu that takes over a touch must stop that running window recognizer, or the glass stays swollen.
- Glass content stays inside glass, live. Glass draws its content lighter than the same content drawn over it, and UIKit tints a one-colour label as it composites (the layer's contents multiply colour), which `CALayer.render(in:)`, `drawText(in:)` and image snapshots all leave out. A transition, morph or menu that moves glass content therefore borrows the real views into the `contentView` of the glass it draws (`TelegramGlassLoan`), as Telegram's transitions lend their content, and gives them back with their constraints. It never draws them as pictures. Content that must hold still while its glass moves gets the opposite motion, on the same spring.
- Inside glass on iOS 27, a view's background color and corner radius move to an effect layer of their own, which doesn't follow animations added to the view's `layer`. A shape that animates inside glass is a plain sublayer.
- TDLib replays a new client's whole state as single updates: about 7000 on every open and every return from the background; after two hours away, 108 of 7628 were new messages. Work per update on the main thread multiplies by that, so what follows from an update goes through a coalesced change, as `TelegramChatListStore.changes` does, and a list page off screen catches up as it appears. Telegram gets this from its Postbox transaction, which its views see as one change.
- The chat list and the archive open search from a button after the bar's left one (`opensSearchFromButton`), with no field under the bar and a bar of fixed height. The button's glass becomes the field and the right buttons' glass the close button, as a chat's search morphs; the search stays open with the keyboard down until its close button. Forum topics and the forward pickers keep the field under the row. Glass and items hidden during an open search leave the stacks over the field, which must not take its touches.
- A screen comes in ready, as Telegram's does: Telegram's NavigationContainer holds a pushed controller until its `ready` signal fires. A screen whose first content loads asynchronously (history, avatar, emoji status, header data) adopts `TelegramTransitionReadiness`; `TelegramNavigationController` then waits for it, for half a second at most, before starting the push. Never animate a first population that the user cannot see yet, and never leave content to pop in after a transition.
